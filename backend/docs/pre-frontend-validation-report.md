# 프론트 연결 전 백엔드 최종 검증 보고서

최종 갱신일은 2026-09-09이다. 사용자 DB와 분리한 MySQL 8.0.44, Java 17, Spring Boot 3.5.16 환경에서 실행했다.

## 결론

프론트 없이 검증 가능한 DB, API 계약, 세션, GPS 스탬프, 도감, 외부 API, 실행 패키지와 관광지 선정 정책이 정상 동작했다. 최신 회귀 테스트는 총 102건 중 92건 통과, 실패·오류 0건이며 환경변수가 필요한 외부 선택 테스트 10건은 기본 실행에서 제외됐다. 실제 MySQL 선정 정책 및 스탬프 통합 테스트도 별도로 통과했다.

서비스 카탈로그는 역사유적 `HS01`, 역사유물 `HS02`, 박물관 `VE070100`, 기념관 `VE070200`, 미술관·화랑 `VE070600`으로 한정했다. 종교성지·안보관광지·랜드마크와 그 밖의 관광·문화 분류는 제공하지 않는다.

## 선정 정책 안전장치

- TourAPI 요청부터 `contentTypeId`와 `lclsSystm1/2/3`를 함께 전달한다.
- 응답 검증에서도 같은 정책을 다시 확인해 공급자 응답 오류가 활성 카탈로그로 들어오지 못하게 한다.
- 세부 분류를 DB에 저장하고 해시 비교에도 포함한다.
- 전국의 모든 선정 조건과 페이지를 완주한 동기화에서만 비선정 행을 비활성화한다.
- 특정 지역 또는 페이지 제한 동기화는 전역 비활성화를 수행하지 않는다.
- 좌표가 누락된 기존 선정 장소는 저장된 정상 좌표를 보존할 수 있다.

## API와 외부 연동

- 헬스체크는 `UP`, Flyway 스키마 버전은 2로 확인됐다.
- 지역, 지도 bounds, 관광지 상세, 익명 세션, 도감, GPS 인증 API 회귀 테스트가 통과했다.
- 전주 지도 bounds 실호출은 활성 장소 33건을 반환했다.
- 16개 광역 도감 요약의 전체 스탬프 합계는 3,885건으로 DB와 일치했다.
- 넓고 밀집된 지도 영역은 `BOUNDS_TOO_DENSE`로 차단되어 프론트가 지도를 확대하도록 유도한다.
- 실제 TourAPI 분류 목록과 카카오 주소 검색·역주소·주변 주차장 호출을 이전 단계에서 검증했다.
- 서버 압축, 세션 쿠키, GPS 멱등성과 동시 요청 제어를 자동 테스트로 확인했다.
- 스탬프 인증 생성 시각을 애플리케이션 UTC로 직접 저장하고, 1분 제한 조회에 현재 시각 상한을 적용해 KST로 잘못 저장된 미래 행이 계속 429를 발생시키는 문제를 수정했다.
- 실제 MySQL에 9시간 미래 시각의 과거 행 5건을 넣은 재현 테스트에서 새 인증 요청이 HTTP 200으로 처리되는 것을 확인했다.
- `localhost:5173` 실제 브라우저에서 카카오 지도·마커, 도감, 관광지 상세, 주변 주차장 화면을 확인했고 최종 콘솔 오류는 0건이다.
- 프론트 의존성 갱신 뒤 남아 있던 Vite 사전 번들 캐시를 재생성하고 HMR 호스트를 `localhost`로 고정했다.

## DB와 배포 준비

- Flyway V1 초기 스키마 뒤 V2 세부 분류 컬럼·인덱스가 정상 적용됐다.
- `tourist_spot.location`은 SRID 4326이며 공간 인덱스를 유지한다.
- 활성 지역 284건과 활성 스탬프 대상 3,885건만 담는 독립 복원용 시드를 생성한다.
- 실행 가능한 Spring Boot JAR과 프론트 프로덕션 빌드를 다시 생성해 확인한다.
- API 키는 소스·문서·데이터 시드·실행 JAR에 넣지 않는다.

## 실제 기기·배포 환경에서 남는 항목

- HTTPS 환경의 `Secure` 쿠키와 운영 도메인 CORS
- 실제 휴대폰 GPS 권한, 정확도와 현장 반경 100m 검증
- 운영 서버·MySQL 부하 및 장애 복구
- 테스트에 사용한 TourAPI·카카오 키 재발급 후 Secret 교체

## 선택 가능한 데이터 보강

전국 시드에는 목록 정보와 대표 이미지 URL이 들어 있다. `detailCommon2` 상세 설명과 `detailImage2` 추가 사진의 전국 수집은 아직 실행하지 않았다. 호출 한도와 화면 요구가 확정되면 활성 3,885건만 증분 보강할 수 있다.
